# Architecture and Technical Decisions

Use this instruction for proposals that affect repository boundaries, service communication, data ownership, tenancy, technology choices, or long-lived conventions.

1. Inspect existing architecture documentation and open ADRs.
2. Identify the real choice, alternatives, constraints, and consequences.
3. Do not select or assume a vendor, protocol, schema, or environment variable merely to remove uncertainty.
4. Keep an ADR factual and mark unresolved matters as TBD.
5. Define the impact on frontend, API, intelligence, contracts, infrastructure, and testing.
6. Create or update only the architecture files owned by the task.

Record a decision in `docs/decisions/` when it is likely to constrain future implementation. Link the ADR from relevant architecture documentation.
